## 3. 已发现缺陷

1. **unfinished 统计死分支（P1）**：`analytics.py:45` 任务查询只取 `assigned/in_progress/paused/overdue`，但 `:59` 试图统计 `overdue/unfinished`。状态为 unfinished 的任务永远不会进入负载，`weighted_overdue_tasks` 不符合文档。复现：插入一个 `unfinished` 任务后查询 `/members/load`。根因：任务状态筛选与展示口径不一致。整改：明确 unfinished 是否计入当前负载；若计入，统一查询和风险口径。
2. **高负载风险仍用计数而非加权（P1）**：`analytics.py:123-124` 用 `member["load_level"]`，而消息写成 `>0.8`。权重后的 high/normal 与风险可能不一致。整改：按已确认口径统一使用 weighted_level，或在文档中明确两个风险阈值。
3. **高优先级未分配任务产生两条风险（P2/待确认设计）**：`analytics.py:118-121` 同时生成 `unassigned_task` 和 `critical_unassigned`；测试也断言并存。需产品确认是保留“普通风险+专项风险”还是去重聚合，不能在整改中自行删除。
4. **LLM 异常静默（P1）**：`analytics.py:99-107` 不保存错误。整改返回脱敏 `llm_error` 或服务端 request id，不得返回密钥/完整响应。
5. **规则与文档“关键任务”优先级不一致风险（P2）**：`RISK_SEVERITY` 设计 95，测试期望并存；需确保前端展示明确“专项风险”而不造成重复计数。

## 4. 权限、前端与真实完整性

- 路由 `routers/analytics.py:16-18,60-67` 先执行 `ensure_project_access`，项目成员可读；本轮静态核验确认调用链，但未覆盖所有跨项目浏览器动作。
- `frontend/src/app/queries.ts:62-66` 工作区加载时并行请求 report/risks/memberLoad/weekly；`optionalJson` 在非 401 错误时返回 null（`:23-29`），前端可能把接口故障显示成“暂无数据”，这是静默降级而非可观测失败。
- `queries.ts:66` 每次 workspace 挂载会访问 weekly-report；配合 `staleTime: 0`（`:48-49`）可能在浏览页面时自动生成/落库周报并触发 LLM，超出“用户主动生成”的可预期行为。

## 5. 整改方案与顺序

1. 先冻结 unfinished、weighted risk、重复 critical 风险的产品口径；
2. 修正 D2 查询和返回字段，保留兼容字段；
3. 增加 LLM 错误可观测性，保持 rule fallback；
4. 调整前端 optionalJson：区分“无数据”“接口错误”“LLM 降级”，禁止把故障伪装为空；
5. 由 D7 做浏览器和 390px 验收。

## 6. 验收标准与剩余风险

风险列表按 severity 降序，所有状态包含 status/due_date，weighted 字段和风险判定口径一致；无 LLM、provider 超时、非法 JSON 均有 rule 结果和可诊断错误；前端能显示错误和降级原因。PostgreSQL、真实 LLM、并发实例尚未实测。
