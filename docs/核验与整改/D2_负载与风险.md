## 3. API 口径与示例

### 3.1 成员负载

对外兼容字段不删除；深化字段附加返回：

- 兼容：`current_task_count`、`max_concurrent_tasks`、`remaining_capacity`、`load_ratio`、`load_level`、`overloaded`；
- 深化：`weighted_load`、`weighted_level`、`weighted_label`、`weighted_overdue_tasks`、`active_statuses`；
- 规则：加权负载为各活动任务状态权重之和除以最大并发数，阈值 `<0.5/0.5-0.8/>0.8` 对应低/正常/高。

### 3.2 项目风险

- 高优先级且未分配：仅一条 `critical_unassigned`；`source_types=["critical_unassigned","unassigned_task"]` 说明它同时覆盖普通未分配语义，`count` 不重复。
- 普通未分配：`unassigned_task`。
- 高负载：依据 `weighted_level`，同时返回原始和加权负载，便于兼容与解释。
- LLM：`llm_status` 明确 `not_configured/failed/ok`；失败仍返回规则总结，但不会伪装成正常规则路径。

## 4. 复现与验证

1. 创建成员，设置最大并发为 3，为其创建两个 `overdue` 任务：原始负载为 $2/3=0.67$（normal），加权负载为 $(1.3+1.3)/3=0.87$（high）；风险必须出现一条 `high_member_load`。
2. 创建一个高优先级未分配任务：按该 `task_id` 过滤风险，必须仅一条 `critical_unassigned`。
3. 清空测试进程 LLM 配置：响应为 `summary_source=rule`、`llm_status=not_configured`、`llm_error=null`。
4. 注入包含测试密钥的异常：响应为 `llm_status=failed`，仍有规则总结，错误只含 `[REDACTED]`，不得出现密钥。
5. 请求 `summarize=0`：响应不含总结字段，模拟 LLM 函数调用次数为 0。
6. 真实 provider：本轮已使用 `.env` 完成一次成功调用，只记录状态、耗时和是否有错误，不记录 prompt、密钥或完整供应商响应。

## 5. 根因与整改记录

1. **口径分裂**：旧代码同时维护计数负载和加权负载，风险仍读取旧字段。整改为风险统一读取 `weighted_level`，旧字段只用于 API 兼容和解释。
2. **重复风险**：同一高优先级任务先进入普通未分配，再进入专项风险。整改为互斥分支，来源语义通过 `source_types` 保存。
3. **静默回退**：LLM 异常被 `except Exception: pass` 吞掉。整改为结构化状态和脱敏错误，规则回退仍保障接口可用。
4. **前端把故障当空数据**：通用 `optionalJson` 返回 null。整改仅对 D2 风险/负载请求增加诊断结果，避免无关查询重构；周报自动写问题留给 D3 专项处理。
