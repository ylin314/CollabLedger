## 4. 缺陷、复现与根因

1. **采纳非事务原子性（P1）**：`recommend.py:685-720` 先调用任务路由更新，再重新连接更新推荐记录；后一步失败会出现任务已改派、推荐仍 generated。复现：在两次写之间注入数据库异常。根因是跨连接、跨事务编排。整改：将任务更新、推荐状态和 recommendation_events 置于同一服务事务；补失败回滚与并发条件更新。
2. **重复点击/竞态（P2）**：`recommend.py:698-711` 状态检查与更新分离，前端 `RecommendationsView.jsx:180-188` 依赖 busy 但批量决定路径仍需核验。复现：并发提交同一 rec_id。整改：数据库条件更新/唯一事件幂等键，前端按钮锁只作体验保障。
3. **历史画像与授权未闭环（P1）**：`recommend.py:426-450` 可跨项目读取画像，但 `GET/PATCH /api/users/me/authorizations` 没有实现（契约 `API接口契约.md:2212-2252`）。复现：成员关闭授权后仍可被其他项目推荐读取。整改依赖 D6 授权模型。
4. **真实 LLM 未验收（P1/外部阻塞）**：测试中的 LLM 都是 monkeypatch/fake；不能把“代码调用存在”写成真实 provider 成功。需外部可用凭据和不输出密钥的 live run。
5. **前端错误边界与 owner/viewer 显示未通过浏览器验收（P2）**：组件存在但无端到端证据。整改依赖 D7 Playwright。

## 5. 整改方案与顺序

1. D6 先完成授权与 profile_source 的数据边界；
2. D1 修复推荐采纳事务/幂等，明确 reviewer 是否联动；
3. 增加少量真实 provider contract test（脱敏、可选、不能依赖 CI 密钥）；
4. D7 执行桌面和 390px 浏览器验收，覆盖生成、排除、采纳、手选、历史和失败提示。

## 6. 验收标准

- 生成推荐只读且四维事实可追溯；
- owner/viewer/超载过滤在数据库事实与 UI 均一致；
- LLM 成功、超时、空 content、非法 JSON 四条路径均有可观测结果且规则回退不静默；
- 采纳一次只产生一次真实指派和一次事件，重试/并发幂等；
- 历史画像只在授权范围内参与计算；
- 浏览器桌面与 390px 均可完成推荐→采纳→历史闭环。
