## 1. 需求基线与已确认产品决策

D1 无独立深化方案。本次以 `docs/团队分工与任务拆解.md:911-943`、`docs/产品路线图.md:99-153`、`docs/API接口契约.md:1230-1295`、项目书，以及 D6 联动要求还原 D1 硬要求；更具体的 API 契约优先于旧方案中“后续路线图/不做”的表述。

已确认并锁定的分支：

1. 推荐采纳只自动修改负责人；界面提示“可选：同时把某人设为评审人”，必须由用户再次确认，绝不偷偷修改 `reviewer_id` 或导师关系。
2. 历史画像授权采用“全局开关 + 按项目白名单/覆盖”两档；默认启用。关闭时冻结并保留数据，另提供删除派生画像数据操作；不删除团队原始任务、贡献和工时记录。
3. API 契约字段是对外标准，深化算法字段作为附加返回字段，不替换契约字段。
4. D2 的高优先级未分配风险聚合为一条；D3 的确认态贡献和工时双列口径沿用后续阶段文档。

## 4. 本轮已完成整改

### 4.1 授权与历史画像边界

- 新增 `profile_authorizations`、`profile_project_authorizations`，schema 版本升至 7，并同步 SQLite 建表与 SQLAlchemy/Alembic 元数据。
- 默认授权为启用；关闭后进入 `frozen`，历史数据不被跨项目读取但仍保留；用户可调用删除派生画像接口进入 `deleted`，团队原始任务/贡献等不删除。
- 当前目标项目的真实数据仍用于同项目推荐；历史来源项目必须同时满足用户参与和授权。本人查看自己的画像不受分享开关影响，但对外成员画像仍受项目隔离。

### 4.2 推荐采纳事务与幂等

- 推荐状态使用 `WHERE ... status='generated'` 条件更新，第二次点击得到 409。
- 任务指派、参与者同步、任务日志、推荐状态和推荐事件共享同一连接/事务；任何异常统一回滚。
- `reviewer_id` 不在采纳服务中写入，避免把评审人或导师关系藏在推荐操作里。

### 4.3 显式评审人确认

- 单任务推荐和批量推荐均在负责人真实更新成功后显示提示；默认不选择评审人。
- 选择后由用户点击“确认设置评审人”才发送任务 PATCH；点击“跳过/知道了”只结束提示，不产生隐藏写操作。
- 只有项目 owner 或任务创建者进入可设置分支；后端仍是最终权限边界，前端判断不作为安全依据。

## 6. 复现方式

1. 在仓库根目录执行 D1 专项回归命令，观察授权默认/冻结/白名单/删除、推荐采纳 200、重复采纳 409、注入异常 500 后数据库回滚。
2. 对临时 SQLite 使用同一 `COLLAB_DB` 启动两次 API 进程，第一进程创建用户、项目、任务和授权记录，停止后第二进程登录并读取同一项目；要求任务和授权状态仍存在。不要用静态 JSON 或 mock 代替该步骤。
3. 使用真实可用的 LLM 配置执行单任务推荐，分别记录成功、超时、空 content、非法 JSON 和 fallback 的 HTTP 响应及服务端脱敏日志；密钥不得写入日志、文档或 Git。
4. 浏览器在桌面和 390px 宽度分别完成：打开推荐页面 → 生成 → 查看排除理由 → 采纳 → 确认/跳过评审人 → 刷新 → 查看负责人、评审人和推荐历史。
