## 3. 测试/实机证据

`test_integrations_github.py` 全部 fake `httpx.post/get`（`:34-54`），覆盖 state、mock 同步、去重、失败、断开；不能证明真实 OAuth、真实网络、重启、token 加密或分页。全量后端 81 passed 只说明测试契约通过。Docker 在本轮环境不可用（2026-08-29 诊断结果），因此没有 Docker/PG 运行证据。

## 4. 复现方式

1. 连接→同步→断开→重新连接→再次同步同一仓库：由于 integration/events 被删，新 integration_id 会再次创建同一贡献。
2. mock commits 成功插入后 pulls 抛异常：检查 contributions/events，`rollback` 会清掉前面成功部分。
3. 在容器环境设置 `.env` 的 GITHUB_* 后运行 `docker compose config`/status：compose 未传变量，status 仍可能 `configured=false`。
4. 以项目 member 调用 sync：当前代码允许，但契约要求 owner，应返回 403。

## 5. 整改路线

D5-0（先决）：确认最终 PRD 是否包含 Webhook 和反向写入；确认外部平台优先顺序和凭据责任。

D5-1：抽 `services/integrations/` 统一 adapter、平台注册、连接/项目绑定/事件/同步接口。
D5-2：token 使用 Fernet/AES-GCM，密钥仅环境注入，state 持久化并绑定 user/session、一次性消费。
D5-3：修复 owner 权限、分页/cursor、部分成功、重试和 stale running 恢复；断开改软失效并保留去重事件。
D5-4：补 GitHub Issue/Review/统计、仓库绑定、events 查询；再按 adapter 接入飞书、腾讯文档/会议，统一转 pending contribution。
D5-5：修复前端回调、source 徽标、owner 门控、移除 `|| 1`；补真实 OAuth/同步验收。

## 6. 验收标准与剩余风险

必须真实走通：连接→回调→项目绑定→同步→事件落库→pending→owner confirm→重复同步去重→断开；另需至少一个文档/会议平台真实主路径。凭据不足时只能标外部阻塞，不能用全 mock 宣称完成。
