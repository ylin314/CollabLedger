## 3. 接口与数据口径

### 3.1 `GET /api/users/me/profile` 与 `/api/users/{id}/profile`

对外契约字段保留；附加字段用于解释内部算法：

- `project_count` 与 `projects_count` 同值。
- `efficiency` 与 `average_efficiency` 同值，都是衰减加权的实际工时/预估工时比，不与打卡工时混加。
- `top_skills` 每项附 `sample_count/source/cold_start`；历史画像不会把 users.skills 计作完成证据。
- `data_sources/source_projects/calculation_notes` 允许用户从响应复算口径。
- `collaboration_types` 仅按 confirmed 贡献的 kind 统计，返回 count 和 ratio。

### 3.2 `GET /api/users/me/collaborations`

合作分公式为：

$$
score = \min(100, 30 \times shared\_project\_count + 5 \times \min(shared\_task\_count, 10))
$$

它只表达共同项目/任务数量，不评价人格、能力、道德，也不用于公开排名。响应返回具体来源项目 ID 和计算说明。

### 3.3 `GET /api/users/me/recommendations`

- 有授权历史任务：按历史技能强度返回方向，附真实任务样本数、数据源和来源项目。
- 无历史但有自报技能：固定 50 分、`cold_start=true`、`sample_count=0`，理由明确“仅自报技能”。
- 冻结或删除：返回空列表和状态说明，不静默生成。

## 4. 根因与本轮整改

1. **原方案只覆盖成员画像弹窗**：缺少契约字段、授权、合作关系和长期方向。整改为统一 profile 聚合和独立 collaboration service。
2. **自报 skills 与历史任务混计**：可能把冷启动标签包装为历史能力。整改后历史强度只来自任务，skills 独立标记。
3. **active_months 读取所有贡献状态**：pending/disputed 可能污染活跃历史。整改 SQL 只读 confirmed。
4. **他人画像曾以历史 membership 作为权限**：成员退出后仍可能读取。整改为 active 共同项目 + 目标授权来源。
5. **授权前端缺失**：用户无法执行已确认的冻结/白名单/删除策略。整改为独立个人入口与显式控件；聊天 Agent 未获得写权限。

## 6. 依赖、阶段顺序与剩余风险

- D6 依赖 D1 推荐兜底、B 的真实项目/任务/成员/贡献数据；本轮未改动 B 业务语义。
- D7 必须继续验证：SQLite 新/旧库、授权重启持久化、PostgreSQL、容器、桌面与 390px 浏览器。
- `cooperation_score` 是透明规则，不应被解释为成员能力排名；未来若修改权重必须版本化并更新契约。
- “彻底删除”当前只删除授权覆盖和派生状态；按需画像没有持久画像表。团队原始事实属于同一真实项目数据，不能因个人关闭而级联删除。
