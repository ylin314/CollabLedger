## 三、已确认问题清单

状态含义：`已实测` 表示 E3 已复现；`静态确定` 表示 E1 已足够判定，但尚未在真实 HTTP/外部环境复现；`外部阻塞` 表示缺少真实账号、服务或网络，不得用 mock 结案。

### P0/P1：必须优先整改

#### A-01 Agent 会话元数据跨用户可写（P0，已实测）

- 现象：同一项目、同一 `session_id` 下，成员可成功 PATCH 组长创建的会话标题，数据库标题被覆盖；聊天正文仍按 `user_id` 隔离。
- 证据：`backend/models.py:162-166` 唯一键只有 `(project_id, session_key)`；`backend/agent/memory.py:55-68` 查找/更新会话未带 `user_id`；`backend/routers/agent.py:131-144` 重命名查询和更新未带当前用户。
- 复现：临时库中 owner 与 member 同项目，owner PATCH 标题后 member 使用相同 session key PATCH，两个请求均 200，最终标题为 member 写入值。
- 整改：把会话元数据所有权纳入查询和唯一约束；历史 NULL 行采取保守迁移策略；列表、重命名、删除、消息恢复统一按当前用户；补同 session key 的双用户 API 测试。
- 验收：member 不能读取或改写 owner 元数据；member 只能看到自己的标题/消息；owner 删除只影响自己的会话数据。

#### A-02 viewer 的 GET 推荐接口产生持久化写入（P1，已实测）

- 现象：`GET /api/projects/{id}/recommendations?task_name=...` 对 viewer 返回 200，同时新增 `recommendations` 和 `recommendation_events` 行。
- 证据：`backend/routers/analytics.py:27` 未提高到写权限；`backend/services/recommend.py:548-566,600` 持久化推荐记录并提交。
- 整改：区分只读预览和明确生成；GET 只读历史/已有结果，生成改为 owner 的显式 POST；若为兼容保留 GET，至少 viewer/member 不得触发写入且接口契约明确。
- 验收：viewer GET 前后数据库行数不变；owner 显式 POST 才能生成记录；重复请求有明确幂等语义。

#### A-03 退出成员仍进入分析和推荐（P1，已实测）

- 现象：将 membership 置为 `left` 后，成员仍出现在 members/load、report、weekly-report 和 recommend 候选；其历史任务仍参与当前统计。
- 证据：`backend/services/analytics.py:44,160,224-228,579-583` 和 `backend/services/recommend.py:360` 查询缺少 `m.status='active'`；`backend/routers/projects.py:197-206` 移除成员只更新 membership，不处理任务/分析边界。
- 整改：统一 active membership scope；当前团队统计排除 left，历史画像按授权规则单独保留；退出时明确任务负责人/参与者的冻结或转交策略，不静默丢数据。
- 验收：退出成员不进入当前负载、报告、推荐候选；历史记录仍按产品规定可追溯；任务无悬空负责人。

#### A-04 归档项目仍可 POST 生成周报（P1，已实测）

- 现象：归档后 `POST /api/projects/{id}/weekly-report` 仍返回 200 并更新周报。
- 证据：`backend/routers/analytics.py:92-106` 只做 member access，没有 `ensure_writable`；生成服务没有项目状态门禁。
- 整改：所有生成/写入路径统一走 `ensure_writable`；归档项目仅允许 GET 历史数据和 restore 后写入。
- 验收：归档项目 POST 返回 409，数据库行不变；恢复后 POST 恢复可用。

#### A-05 OAuth state TTL 消费校验失效（P1，静态确定）

- 现象：`_state_expired` 将传入的 `expires_at` 当作 created 时间比较，导致当前时间未达到未来 expires_at 时恒为未过期，600 秒 TTL 不能按设计阻止消费。
- 证据：`backend/routers/integrations.py:81-86,109`，清理过期行不等于消费时拒绝。
- 整改：消费时直接比较 `now >= expires_at`，并在数据库条件中同时校验 `expires_at > now`；增加过期、重放、跨用户、跨 session 测试。
- 验收：过期 state 无法换 token；跨进程/重启仍正确；一次消费后再次请求失败。

#### A-06 D5 外部主路径未完成（P1，外部阻塞）

- 范围：GitHub OAuth→绑定→四类事件同步→pending→confirm→重复同步→Webhook→反向 Issue/PR→断开/重连；飞书 OAuth/Wiki/Docx；腾讯文档真实 API。
- 当前证据：本地适配器和测试替身存在，当前运行库虽有 active connection 记录，但 `project_integrations=0`、`last_synced_at=NULL`，不能判定项目真实接入；旧核验文档记录三平台凭据为空。
- 整改：先修本地状态和安全问题，再在隔离资源上做 E4 live run；缺凭据时维持外部阻塞，不得改成假成功。
- 验收：每个平台都必须有授权、项目绑定、实际同步、事件/贡献落库、去重、断开/重连和失败可诊断证据。

### P2：必须在闭环完成前整改

#### B-01 参与者 PATCH 权限可被普通 member 绕过（P1，已实测）

- 现象：普通项目 member 只提交 `participant_ids` 即可 PATCH 任务并改变参与者，返回 200；参与者随即获得任务状态/打卡权限。
- 证据：`backend/routers/tasks.py:102` 先 pop `participant_ids`；`backend/routers/tasks.py:116-136` 非 owner 权限判断只覆盖剩余字段。
- 整改：participant_ids 必须归入 owner/reviewer 管理字段权限；成员只能修改被允许的 `actual_hours` 等字段；变更前后校验 assignee、参与者、reviewer 的一致性。
- 验收：member 修改 participant_ids 返回 403；owner 修改成功并写审计；任务动作权限随参与者状态正确变化。

#### B-02 逾期未分配任务产生重复风险（P1，已实测）

- 现象：同一任务同时生成 `critical_unassigned` 和 `overdue_task` 两条风险。
- 证据：`backend/services/analytics.py:127-136` 两个独立 if；临时任务 `status=unassigned,due_date<today` 返回 2 条。
- 整改：风险按 task_id 归并，`source_types` 保留来源，优先级使用最高 severity；`unfinished` 与 overdue 的业务语义分离。
- 验收：每个 task_id 在风险结果最多一条；source_types 完整；排序稳定。

#### B-03 推荐使用计数负载而非 weighted 负载（P1，静态确定）

- 证据：`backend/services/recommend.py:409-414` 使用 `current/maximum`，没有读取 `weighted_load/weighted_level`；D2 方案要求推荐优先使用加权负载。
- 整改：推荐候选、超载排除和理由使用统一 weighted 口径，兼容字段仅作为展示。
- 验收：同一成员在 overdue 加权 high 场景下不会被推荐；API、Agent 和前端显示一致。

#### B-04 周报“本周”按 updated_at 归属，评价会污染周归属（P1，静态确定）

- 证据：`backend/services/analytics.py:184-188,211-222,233-235` 使用 updated_at；`backend/routers/tasks.py:287` 评价更新任务 updated_at。
- 整改：新增并使用完成时间/状态变更时间等稳定事实；历史兼容时明确迁移规则，不以评价时间代替完成时间。
- 验收：上周完成、本周评价的任务不计入本周完成和工时；当前快照字段与周内字段命名分开。

#### B-05 前端负载口径分裂（P1，静态确定）

- 证据：`frontend/src/shared/components.jsx:47` 使用 `load_level`；`frontend/src/features/overview/Overview.jsx:42-44` 使用 `weighted_level`；`frontend/src/App.jsx:270-273` 排除 overdue，而后端 active statuses 包含 overdue。
- 整改：统一前端展示和筛选为 weighted 口径，显式展示计数原始字段，避免同一成员同时显示 normal 和 high。
- 验收：API、总览提醒、成员卡片、推荐卡片对同一数据给出同一结论。

#### B-06 LLM 错误在周报/推荐路径未统一脱敏（P1，静态确定）

- 证据：`backend/services/analytics.py:354-355,385-386`、`backend/services/recommend.py:255-256,289-290,328-329` 直接写 `str(exc)`；错误会返回前端并写入 weekly/recommendation payload。
- 整改：共用 Agent 的安全错误函数或独立 `_safe_llm_error`；错误持久化只留错误类别、request id 和截断后的脱敏摘要。
- 验收：注入包含 Authorization/API key/token 的异常，响应、数据库、日志均无敏感片段。

#### B-07 D4 Agent 工具数据库路径不一致（P1，静态确定）

- 证据：`backend/agent/tools.py:86-103` 的 platform_activity 直接 `connect()`，不复用 AgentRuntime 的 `db_path`；测试 monkeypatch `DB_PATH` 时可能读到另一数据库。
- 整改：所有 Agent 工具通过统一的受控只读连接/仓库注入，明确 project_id 和数据库来源。
- 验收：临时数据库 Agent 只读取临时库；生产库和测试库不会串读。

#### B-08 D6 协作履历未承接画像授权（P1，静态确定）

- 证据：`backend/routers/classrooms.py:60-75` 只校验共同 active classroom，返回目标用户全部 projects/tasks/contributions；未使用 `profile_source_project_ids` 或双方授权。
- 整改：履历返回按当前班级/项目和双方授权过滤；区分当前协作事实与跨项目画像。
- 验收：同班但无授权的无关项目不会出现；双方授权撤销后立即消失。

#### B-09 退出项目任务负责人/参与者处置不完整（P1，静态确定）

- 证据：`backend/routers/projects.py:197-206` 退出只更新 membership；任务仍引用用户。
- 整改：退出策略与 B-01/A-03 联动，采用明确的转交、冻结或待处理状态；所有变更写审计。
- 验收：无 active 成员被显示为当前负责人；任务仍可被 owner 处置。

#### C-01 历史项目页与 API 契约断链（P1，静态确定/待浏览器复现）

- 契约要求 `GET /api/users/me/history` 支持过滤和分页并返回历史项目字段；当前前端主要过滤 `/api/projects` 的 active 列表，未调用该契约接口。
- 证据：`backend/routers/classrooms.py:76-79` 复用协作履历结构；`frontend/src/App.jsx:687-691`；`frontend/src/features/projects/HistoryProjectsView.tsx`。
- 整改：实现契约接口与前端 query 绑定，补空态、错误态和真实历史项目数据。
- 验收：归档项目能在历史页出现；筛选/分页与响应字段可用；无历史时诚实显示空态。

#### C-02 班级成员页面 390px 横向溢出（P1，已实测）

- 现象：viewport 390 CSS px 下 document client width 375、scroll width 395；成员列表元素超出可视区。
- 整改：收敛列表最小宽度、长邮箱/技能换行和成员卡布局；只作用于班级成员组件，不污染全局表格。
- 验收：390px、375px、桌面视口均无横向滚动；成员数据、按钮和空态仍可用。

#### C-03 前端错误/静默失败与 E2E 覆盖缺口（P2，静态确定）

- 重点：历史项目、平台回调、viewer/member 权限、推荐空候选、重试、网络超时和重复点击仍缺完整桌面+390px矩阵。
- 整改：统一 ApiError 展示、操作锁定、重试和空/错误/降级状态；补核心链路的最小浏览器矩阵。
- 验收：所有主按钮都有成功、失败、加载、空态；错误不静默，不能出现假成功。

## 五、原子提交与独立复核规则

1. 每个阶段按单一能力拆成独立提交，不把文档、权限、UI 和外部平台无关改动混成一个提交。
2. 每次修改前检查 `git status` 和 `git fetch origin --prune`；不得覆盖用户未提交文件。
3. 每个原子提交后执行：相关 pytest → 后端/前端构建 → Docker 健康 → 目标 API → 必要 Playwright。
4. 每阶段完成后开启独立只读 review，review 只检查该阶段 diff、权限、契约、错误处理、测试覆盖和真实证据；发现 P0/P1 必须修复后再次 review。
5. 仅在本地验证和独立 review 通过后，原子提交并推送 `main`；不 force push、不 merge 非本次变更、不删除非本次创建的资源。
6. 任何外部写入（真实 GitHub Issue/PR、Webhook、飞书/腾讯文档）必须记录资源范围和回滚方式；无凭据时不创建伪产物。
