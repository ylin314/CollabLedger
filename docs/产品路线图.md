# 《协作账本》产品路线图

## 阶段一：基础功能

### 目标

完成真实小组可日常使用的协作闭环，形成上线 MVP 的核心能力。

### 功能范围

1. 创建项目组
2. 邀请成员
3. 创建任务
4. 任务状态管理
5. 成员主动打卡
6. 任务完成质量评价
7. 项目进度看板

### 具体任务

| 模块 | 任务 | 说明 |
| --- | --- | --- |
| 创建项目组 | 项目创建表单 | 支持项目名称、项目类型、简介、开始日期、结束日期 |
| 创建项目组 | 项目详情页 | 展示项目基础信息、成员列表、任务统计 |
| 邀请成员 | 邀请链接 / 邀请码 | 组长生成邀请，成员注册或登录后加入项目 |
| 邀请成员 | 成员角色 | 区分组长、组员、只读成员 |
| 创建任务 | 任务创建表单 | 支持标题、描述、负责人、截止日期、预计工时、任务类型 |
| 任务状态管理 | 状态流转 | 未分配、已分配、进行中、暂停、已完成、延期、未完成 |
| 任务状态管理 | 操作日志 | 记录操作者、操作时间、状态变化和备注 |
| 成员主动打卡 | 工作日志打卡 | 成员主动填写做了什么、耗时、产出和遇到的问题 |
| 成员主动打卡 | 隐私边界 | 不采集在线时长、屏幕、键鼠、位置等行为数据 |
| 任务完成质量评价 | 质量评分 | 任务完成后由组长或指定评审人打分 |
| 任务完成质量评价 | 评分记录 | 保存评分人、评分时间、评分依据和分数 |
| 项目进度看板 | 总体进度 | 展示任务总数、已完成、进行中、延期、未分配 |
| 项目进度看板 | 成员视图 | 展示成员任务数量、完成数量、延期数量和当前负载 |

### 交付物

- 项目创建与项目详情页面
- 邀请成员流程
- 任务创建与任务列表
- 任务状态流转和操作日志
- 成员工作日志打卡功能
- 任务质量评价功能
- 项目进度看板

### 验收标准

- 组长可以创建项目组并邀请成员加入。
- 组长可以创建任务并指派给成员。
- 成员可以更新任务状态并主动填写工作日志。
- 组长可以对已完成任务进行质量评价。
- 项目进度看板数据与真实任务状态一致。
- 所有任务状态变化都有操作记录。
- 不采集任何私人行为数据。

### 上线前置要求

虽然账号与权限没有列入原始功能清单，但阶段一实际开发时必须包含：

- 用户注册、登录、退出
- 项目数据隔离
- 项目角色权限
- 数据库迁移
- 基础测试和部署


### 依赖

- 无外部平台依赖。
- 建议先完成账号体系和权限模型。

## 阶段二：AI 功能

### 目标

基于阶段一沉淀的任务、技能、负载、质量数据，为组长提供可解释的协作决策辅助。

### 功能范围

1. 未分配任务推荐
2. 成员负载分析
3. 任务匹配度计算
4. AI 推荐理由
5. 项目风险提醒
6. 周报自动生成

### 具体任务

| 模块 | 任务 | 说明 |
| --- | --- | --- |
| 未分配任务推荐 | 候选人推荐 | 对未分配任务生成候选成员列表 |
| 未分配任务推荐 | 负载过滤 | 达到最大并发任务数的成员不进入候选列表 |
| 成员负载分析 | 当前负载 | 统计进行中、已分配、暂停任务数量 |
| 成员负载分析 | 负载预警 | 标记高负载和低负载成员 |
| 任务匹配度计算 | 技能匹配 | 根据成员技能、任务标题和任务类型计算匹配度 |
| 任务匹配度计算 | 历史质量 | 根据已完成任务质量评分计算可靠性 |
| 任务匹配度计算 | 历史效率 | 根据预计工时和实际工时计算效率 |
| AI 推荐理由 | 因素解释 | 输出技能、质量、效率、负载四个维度的解释 |
| AI 推荐理由 | 建议文案 | 生成自然语言推荐理由 |
| 项目风险提醒 | 延期风险 | 识别已延期、临近截止和无负责人任务 |
| 项目风险提醒 | 负载风险 | 识别成员负载过高或关键任务无人承接 |
| 周报自动生成 | 项目周报 | 汇总本周任务完成、进行中、延期和工作日志 |
| 周报自动生成 | 成员摘要 | 生成成员工作产出摘要 |

### 交付物

- 未分配任务推荐接口
- 成员负载分析模块
- 任务匹配度计算模块
- AI 推荐理由展示
- 项目风险提醒
- 周报自动生成

### 验收标准

- 未分配任务可以生成候选人列表。
- 推荐结果包含分数和可解释理由。
- 超负载成员不会被继续推荐。
- 推荐理由可以追溯到具体事实数据。
- 风险提醒能覆盖延期任务、临近截止任务和无负责人任务。
- 周报基于真实项目数据生成，不虚构事实。
- 页面明确提示“推荐仅供参考，最终由组长决定”。

### 依赖

- 阶段一的任务状态、负责人、技能、工时和质量评分数据。
- 若数据不足，推荐和周报质量会明显下降。

## 阶段三：贡献系统

### 目标

从单一任务管理升级为可追溯、可确认的项目贡献账本，为期末互评和项目复盘提供依据。

### 功能范围

1. GitHub 接入
2. Git Commit 统计
3. 文档贡献记录
4. 会议纪要
5. 贡献报告

### 具体任务

| 模块 | 任务 | 说明 |
| --- | --- | --- |
| GitHub 接入 | OAuth 登录 | 成员绑定 GitHub 账号 |
| GitHub 接入 | 仓库绑定 | 组长为项目绑定 GitHub 仓库 |
| GitHub 接入 | 数据同步 | 拉取 Commit、Pull Request、Issue 等公开协作数据 |
| Git Commit 统计 | 提交统计 | 按成员统计提交数量、变更行数、参与时间 |
| Git Commit 统计 | 多指标统计 | 不只用 commit 数评价贡献，同时参考 PR、Review、Issue |
| 文档贡献记录 | 手动记录 | 支持记录文档、调研、设计、测试等非代码贡献 |
| 文档贡献记录 | 证明链接 | 支持填写文档链接、截图或说明 |
| 会议纪要 | 会议记录 | 记录会议时间、参与者、结论和行动项 |
| 会议纪要 | 行动项关联 | 将会议行动项关联到任务 |
| 贡献报告 | 个人报告 | 汇总成员任务、代码、文档、会议等贡献 |
| 贡献报告 | 项目报告 | 汇总项目整体贡献结构和完成情况 |
| 贡献报告 | 导出能力 | 支持导出 Markdown 或 PDF |

### 交付物

- GitHub OAuth 与项目仓库绑定
- Git Commit / PR / Issue 统计
- 手动文档贡献记录
- 会议纪要模块
- 个人贡献报告和项目贡献报告

### 验收标准

- 成员可以绑定 GitHub，并授权系统读取指定仓库数据。
- 系统能按成员同步并统计代码协作数据。
- Commit 数量不作为唯一贡献标准。
- 成员可以补充说明代码贡献背景。
- 文档、调研、会议等非代码贡献可以手动记录。
- 贡献报告可追溯每一条记录来源。
- 贡献报告不做公开成员排名。

### 依赖

- 阶段一账号体系和项目权限。
- GitHub OAuth 应用配置。
- 组长和成员明确授权范围。
- 建议在正式接入前先支持手动贡献记录。

## 阶段四：长期协作

### 目标

利用多项目、多学期的数据积累，帮助成员沉淀长期协作画像，帮助组长更高效组建后续团队。

### 功能范围

1. 历史项目
2. 个人协作画像
3. 跨项目合作关系
4. 长期任务推荐

### 具体任务

| 模块 | 任务 | 说明 |
| --- | --- | --- |
| 历史项目 | 项目归档 | 项目结束后归档，保留任务、贡献和报告 |
| 历史项目 | 历史查询 | 用户可以查看自己参与过的历史项目 |
| 个人协作画像 | 画像生成 | 基于任务完成质量、效率、稳定性、协作类型生成画像 |
| 个人协作画像 | 画像自览 | 成员可以查看自己的画像和数据来源 |
| 个人协作画像 | 数据授权 | 跨项目使用个人数据前需要用户明确授权 |
| 跨项目合作关系 | 合作次数 | 统计两个成员共同参与的项目和协作频率 |
| 跨项目合作关系 | 合作效果 | 结合任务完成质量与延期情况描述合作效果 |
| 长期任务推荐 | 长期匹配 | 基于历史多项目表现推荐成员 |
| 长期任务推荐 | 冷启动处理 | 对新用户继续使用技能和负载规则推荐 |

### 交付物

- 历史项目归档与查询
- 个人协作画像
- 跨项目合作关系分析
- 长期任务推荐

### 验收标准

- 用户可以查看自己参与的历史项目。
- 个人画像只基于项目成果和公开协作事实。
- 用户可以查看画像的数据来源和计算逻辑。
- 跨项目使用个人数据必须获得授权。
- 画像不输出人格评价、道德评价或公开排名。
- 新用户缺少历史数据时仍可获得合理推荐。


### 依赖

- 前三个阶段的数据积累。
- 明确的隐私政策和数据授权规则。
- 足够数量的真实项目和真实协作记录。

## 总体优先级

| 阶段 | 优先级 | 判断 |
| --- | --- | --- |
| 阶段一：基础功能 | P0 | 上线 MVP 核心，必须优先完成 |
| 阶段二：AI 功能 | P1 | 提升分配效率和复盘效率，依赖阶段一数据 |
| 阶段三：贡献系统 | P1 | 提升贡献可信度和期末评价价值 |
| 阶段四：长期协作 | P2 | 需要数据积累和授权体系，适合后期演进 |

## 阶段依赖关系

```text
阶段一：基础功能
  ↓
阶段二：AI 功能
  ↓
阶段三：贡献系统
  ↓
阶段四：长期协作
```

说明：

- 阶段二是阶段一的数据消费方。
- 阶段三的 GitHub 接入依赖账号体系，手动贡献记录可以提前。
- 阶段四依赖多项目历史数据，不应提前过度设计。


## 总体风险

| 风险 | 阶段 | 应对 |
| --- | --- | --- |
| 权限模型缺失 | 阶段一 | 先做注册登录、项目隔离和角色权限 |
| 任务数据不规范 | 阶段二 | 强制维护负责人、截止日期、工时和质量 |
| 推荐不可解释 | 阶段二 | 优先使用规则模型，输出推荐理由 |
| Commit 被滥用为唯一指标 | 阶段三 | 引入 PR、Review、Issue 和手动说明 |
| 贡献造假 | 阶段三 | 增加证明链接、组长确认和贡献状态 |
| 用户不信任画像 | 阶段四 | 允许用户自览、追溯来源、明确授权 |
| 冷启动无历史数据 | 阶段四 | 保留技能和负载规则推荐 |
